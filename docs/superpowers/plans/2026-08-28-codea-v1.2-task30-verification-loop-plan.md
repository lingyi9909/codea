# Task 30 Deterministic Verification Loop Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make machine verification—not model prose—the authority for whether a mutating Codea task is complete, and automatically drive a bounded evidence-based repair loop when verification is missing or fails.

**Architecture:** Add a guarded enterprise `verify_project` tool that detects a local project verification profile and executes fixed safe argv stages through existing execution/security infrastructure. The plugin emits explicit safe verification metadata. Application reduces mutation + verification tool events into `TaskExecutionState`, intercepts Runtime step completion, and either accepts completion, issues one bounded synthetic continuation to verify/fix, or ends truthfully as failed/unverified. No Verifier LLM Agent is introduced.

**Tech Stack:** Bun 1.3.14/TypeScript plugin tools, existing `execCommand`/RuntimeSecurityGuard/DLP/audit, Go 1.26.5 Application/Live Trace, Maven/Gradle/Go local project tooling, existing Codea Runtime contract.

**Spec:** `docs/superpowers/specs/2026-08-28-codea-v1.2-agent-intelligence-reliability-design.md` §7

## Global Constraints

- Hard rule: **mutation + no fresh successful same-task verification = no verified completion**.
- Never infer test/build success from assistant text.
- Never add a Verifier Agent or ask an LLM to decide whether command output means PASS.
- `verify_project` accepts only a bounded schema; no arbitrary command string/extra args.
- Reuse existing `execCommand`, RuntimeSecurityGuard, approval, command policy, DLP, audit, and project-root binding.
- Verification must not bypass the Task 29 plan gate.
- Unknown build system/configuration returns `NOT_CONFIGURED`, never PASS.
- Public internet is not required. Do not force external repositories or download verification tooling.
- Existing project wrapper scripts are preferred where applicable.
- Automatic repair is bounded; default maximum is 2 control continuations per root task.
- A control continuation is synthetic Codea context, not a visible fake user message.
- Existing session/Agent/model identity remains stable across the repair loop.
- Windows 10/11 x64, no WSL, paths with spaces are mandatory.
- TDD and factual machine evidence only.
- Direct commits to `develop`; never force push.

```ts
export type VerificationCategory =
  | "PASS"

  | "TIMEOUT"
  | "NOT_CONFIGURED"

  category: VerificationCategory;

  outputSummary: string;
```

- [ ] **Step 1: Write RED schema tests**

```text

args field → invalid
unknown property → invalid

```

Use default stage timeout 180 seconds and hard maximum 600 seconds.

- [ ] **Step 2: Define deterministic overall result**

Rules:

```text

any required/optional executed stage FAIL → FAIL
any stage TIMEOUT → TIMEOUT
profile unknown → NOT_CONFIGURED
internal execution/setup failure → ERROR
```

An optional static stage is optional only when not configured. If detected/configured and then fails, overall result is FAIL.

Failed:

```text
Codea verification gate: the latest verify_project result failed. Inspect the verification evidence already available in this session, update the current plan step as needed, make the smallest justified fix, rerun verify_project, and stop if the bounded repair attempt cannot produce PASS.
```

## Task 30 Done Criteria

Task 30 is complete only when:

- `verify_project` executes fixed local profiles through existing security controls;
- verification emits explicit safe machine metadata;
- Application tracks freshness after mutation;
- mutating task without fresh PASS cannot render verified completion;
- failed/missing verification triggers at most two automatic control continuations;
- retry exhaustion stops automatically;
- unknown build configuration is never converted to PASS;
- Agent prose cannot override the gate;
- existing Task 25 trace/session/approval and professional Agent regressions stay green;
- Windows/native/offline constraints remain green;
- human acceptance is recorded separately.
