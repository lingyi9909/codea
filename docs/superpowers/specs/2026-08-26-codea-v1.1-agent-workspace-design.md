# Codea V1.1 Agent Workspace Design

Date: 2026-08-26
Status: Approved design for implementation
Target branch: `develop`
Scope: Task 22–26
Runtime baseline: OpenCode `v1.18.11`

## 1. Goal

Codea V1.1 upgrades the current custom TUI from a functional chat shell into a complete enterprise Agent workspace.

The goal is not to copy the full OpenCode native TUI. Codea keeps OpenCode as the runtime provider while owning the product experience, command system, Agent routing, enterprise controls, conversation UX, and execution trace.

Target product shape:

```text
Codea
├── Chat
├── Command Palette
├── Agent Workspace
├── Session Workspace
├── Model Workspace
├── Skill Workspace
├── Enterprise Commands
├── Project Commands
├── Enterprise Agents
├── Conversation UX
├── Live Execution Trace
├── Security / DLP / Approval
└── OpenCode Runtime
```

Architecture remains:

```text
TUI
 ↓
Application
 ↓
Codea-owned AgentRuntime Contract
 ↓
OpenCodeAdapter
 ↓
OpenCode v1.18.11
```

The TUI and Application layers MUST NOT depend on OpenCode vendor DTOs or OpenCode-specific API objects.

## 2. Product principles

1. Normal natural-language chat remains the primary interaction path.
2. `/` commands provide explicit workspace operations without forcing users to memorize hidden shortcuts.
3. Professional commands route directly to controlled Codea Agents; they MUST NOT be translated into vague prompts for the General Agent.
4. Runtime-specific capabilities remain behind the Codea-owned Runtime Contract.
5. Enterprise and project extensibility must be fail-closed and must not allow project files to override controlled built-ins.
6. User, Agent, System, and execution activity must be visually distinguishable.
7. Users must always be able to tell whether Codea is thinking, running tools, waiting for approval, or preparing an answer.
8. Agent / Skill / Plugin / Tool / Subagent activity is execution telemetry, not hidden model reasoning, and should be visible by default at an appropriate detail level.
9. Trace rendering must preserve DLP, sensitivity, truncation, and secret-safety rules.
10. V1.1 should borrow proven interaction patterns from Claude Code for waiting states and tool-call presentation, while retaining Codea branding and enterprise semantics. This is an interaction-pattern reference, not a pixel-for-pixel or branded clone.

V1.1 is delivered in five Tasks:

# Task 22 — Command Workspace

## 22.1 Objective

Introduce a first-class Codea command system and Command Palette so Codea behaves like a real workspace rather than a chat box with scattered keyboard shortcuts.

## 22.2 Built-in commands

V1.1 built-ins:

```text
/help
/clear
/status
/sessions
/skills
/agents
/cancel
/doctor
```

Task 23 and Task 24 add additional built-ins through the same registry:

```text
/model
/compact
/review
/test
/api-doc
/debug
/view
```

## 22.3 Command Registry

Create a centralized `CommandRegistry`. Command behavior MUST NOT be implemented as an expanding set of ad-hoc `if input == "/xxx"` branches in Bubble Tea update handlers.

A command definition should own at least:

```text
Name
Aliases
Description
Category
Source
Arguments / usage
Handler or route
RequiredCapability (optional)
Agent route (optional)
Availability
```

Suggested sources:

```text
builtin
enterprise
project
```

## 22.4 Parser and execution semantics

- Input beginning with `/` is parsed as a command.
- Unknown commands produce a clear user-visible command error and MUST NOT be sent as a normal model prompt.
- A command with arguments preserves argument text exactly enough for downstream command/Agent routing.
- Built-in handlers return structured application outcomes rather than directly mutating vendor-specific runtime state.
- Command execution must be testable without a terminal.

## 22.5 Command Palette UX

Typing `/` opens the palette immediately.

Required behavior:

```text
/           → open palette
/re         → live-filter to matching commands
↑ / ↓       → move selection
Enter       → execute selected command
Esc         → close palette
```

Direct full command input remains supported:

```text
/review OrderService
/sessions
/status
```

While the palette is open, palette keys MUST NOT leak into chat input or trigger unrelated shortcuts.

## 22.6 Custom commands

Support exactly two custom-command scopes in V1.1:

Enterprise distribution scope:

```text
distribution/commands/*.md
```

Project scope:

```text
.codea/commands/*.md
```

No user-personal command directory in V1.1.

Suggested Markdown contract:

```yaml
---
name: check-order
description: Check the order module
agent: code-reviewer
---

Review the order module using the supplied arguments:

$ARGUMENTS
```

## 22.7 Conflict policy

Priority is fixed:

```text
Built-in > Enterprise > Project
```

Lower-priority definitions MUST NOT override higher-priority commands.

Any name/alias collision must fail closed with a deterministic machine code such as:

```text
COMMAND_CONFLICT
```

A project must never be able to replace `/review`, `/test`, `/api-doc`, `/debug`, `/doctor`, `/model`, or any other controlled built-in behavior.

## 22.8 Task 22 acceptance gate

PASS requires all of the following:

- `/` opens the palette.
- Live filtering works.
- Keyboard selection works.
- Full command input works without opening the palette first.
- Unknown slash commands never reach the model.
- Palette modal input cannot leak into chat.
- Enterprise commands load from `distribution/commands/*.md`.
- Project commands load from `.codea/commands/*.md`.
- Conflict handling is deterministic and fail-closed.
- Existing keyboard shortcuts continue to work unless explicitly replaced by an equivalent command.
- General chat regression remains green.

# Task 23 — Runtime Workspace

## 23.1 Objective

Expose the runtime capabilities required by a complete Agent workspace without leaking OpenCode-specific objects into the application.

Existing capabilities such as session listing/history, Agent listing, cancellation, Skills, Doctor, and health/status should be reused rather than duplicated.

## 23.2 `/model`

Model selection is session-scoped.

Desired behavior:

```text
/model
  ↓
List available models
  ↓
User selects model
  ↓
SessionState.SelectedModel
  ↓
Future PromptRequest.Model uses that selection
```

Important design constraint:

`PromptRequest` already contains Codea-owned `ModelRef`, therefore V1.1 SHOULD NOT add a stateful `AgentRuntime.SetModel()` solely for UI preference.

Add a Codea-owned runtime capability equivalent to:

```go
ListModels(ctx context.Context) ([]Model, error)
```

Model DTOs exposed above the adapter must be Codea-owned.

Each session can use a different selected model. A new session starts with the configured/default model unless explicitly changed.

## 23.3 `/compact`

`/compact` means real current-session context compaction.

Required semantics:

```text
Current Session
  ↓
CompactSession
  ↓
Runtime produces/retains compacted context or summary
  ↓
Continue the same Session
```

It MUST NOT mean:

- delete conversation history;
- fake compaction by clearing TUI state;
- silently create a new session unless a future runtime contract explicitly defines such behavior.

Add a Codea-owned capability equivalent to:

```go
CompactSession(ctx context.Context, sessionID SessionID) error
```

and a capability flag such as:

```text
RuntimeCapabilities.Compaction
```

If the active runtime cannot compact, Codea must show a deterministic Unsupported result rather than pretending success.

## 23.4 `/status`

The status view should expose useful workspace context, for example:

```text
Codea Version
Runtime Provider
Runtime Version
Runtime Health
Project
Session
Current Agent
Current Model
Skill Mode
Loaded Skills
Streaming support
Reasoning support
Tool approval support
Compaction support
```

Status rendering should not expose secrets, credentials, or sensitive raw configuration.

## 23.5 `/doctor`

The TUI `/doctor` command and CLI `codea doctor` MUST share the same underlying Doctor service/use-case implementation. Do not maintain duplicate validation logic.

## 23.6 Session / Agent / Skill workspace behavior

- `/sessions` reuses existing session APIs and history rehydration.
- Session switching is blocked while an incompatible in-flight operation is active unless that operation is cancelled first.
- Switching sessions resets transient streaming/reasoning/tool state so activity cannot bleed between sessions.
- `/agents` uses the runtime Agent list and Codea Agent metadata.
- `/skills` reuses the current Skill manager/policy implementation.
- `/cancel` cancels the active session operation through the Runtime Contract.

## 23.7 Task 23 acceptance gate

PASS requires:

- Vendor DTO zero-leakage from `runtime/opencode` into Application/TUI.
- `/model` lists real runtime-available models.
- Model selection is isolated per session.
- Selected model is actually applied to subsequent prompts.
- `/compact` performs real runtime compaction.
- Unsupported compaction is explicit and fail-closed.
- Session resume does not leak prior session transient state.
- `/doctor` and CLI Doctor share implementation.
- Existing OpenCode v1.18.11 adapter tests remain green.
- Runtime abstraction remains suitable for a future non-OpenCode adapter.

# Task 24 — Professional Agent Workspace

## 24.1 Objective

Turn the existing enterprise Agents into stable, discoverable workspace capabilities.

Professional commands:

```text
/review
/test
/api-doc
/debug
```

## 24.2 Deterministic Agent routing

Routes are fixed:

```text
/review   → Code Reviewer Agent
/test     → Unit Test Generator Agent
/api-doc  → API Documentation Agent
/debug    → Debug Agent
```

A professional command MUST route directly to its configured Agent.

Forbidden behavior:

```text
/review → General Agent → ask model to decide whether/how to review
```

Command arguments become the task input for the professional Agent.

## 24.3 Existing Agents

Reuse the existing first-class enterprise Agents:

```text
code-reviewer
unit-test-generator
api-documentation
```

Do not duplicate their prompts, Skills, permissions, or Tool policy in the command layer.

## 24.4 New Debug Agent

Add a first-class controlled Debug Agent and corresponding Debug Skill.

Suggested distribution paths:

```text
distribution/agents/debug/
distribution/skills/debug/
```

Primary scope:

```text
Test failures
Build/compile failures
Runtime errors
Log analysis
Bug reproduction
Root-cause analysis
Code fix
Post-fix verification
```

Debug workflow:

```text
Collect evidence
  ↓
Reproduce when feasible
  ↓
Locate failure
  ↓
Determine root cause
  ↓
Propose/perform controlled fix
  ↓
Re-run relevant verification
  ↓
Report outcome
```

Role boundary:

```text
Code Reviewer → identify issues in code/change
Debug Agent   → investigate an observed failure and drive it to verified resolution
```

The Debug Agent must inherit the same enterprise security principles: Tool restrictions, approvals, DLP, Skill policy, and offline constraints.

## 24.5 Agent workspace mode

Users may invoke a one-shot professional command:

```text
/review OrderService
```

or switch the current working Agent through `/agents` and continue multi-turn interaction with that Agent.

The UI must clearly show the currently active Agent.

## 24.6 Task 24 acceptance gate

PASS requires:

- All four professional commands route to exact expected Agents.
- No General-Agent fallback for professional commands.
- Existing three Agents are reused, not duplicated.
- Debug Agent and Debug Skill are first-class distribution artifacts.
- Agent permissions are enforced server-side/runtime-side as designed.
- Agent switching is visible and session-safe.
- Professional command arguments arrive intact at the selected Agent.
- Existing Code Reviewer / Unit Test / API Documentation regressions remain green.
- Debug end-to-end tests cover at least failure diagnosis, fix path, and re-verification behavior.

# Task 25 — Claude-style Conversation UX & Live Trace

## 25.1 Objective

Redesign the conversation experience so the user can immediately distinguish who is speaking and can continuously see what Codea is doing.

The interaction pattern should take inspiration from Claude Code's mature terminal UX for waiting states, tool-call summaries, compact activity history, and expandable detail. Codea must keep its own branding, enterprise semantics, and trace model.

## 25.2 Conversation roles

The TUI must visually distinguish at least:

```text
YOU
CODEA / ACTIVE AGENT
SYSTEM
ACTIVITY
```

Target interaction shape:

```text
❯ 帮我 review OrderService 最近的修改

● Code Reviewer · qwen3-coder

  ...
```

System/runtime notices should use a separate visual identity and must not look like an Assistant answer.

Avoid excessive boxes around every line. Prefer a clean terminal hierarchy with spacing, typography, prefixes, indentation, and restrained styling.

## 25.3 Live waiting indicator / spinner

Replace the current static `Working` indicator with a real animated spinner, for example:

```text
⠋ ⠙ ⠹ ⠸ ⠼ ⠴ ⠦ ⠧ ⠇ ⠏
```

The user must see continuous activity while a response is in progress.

The visible status text should follow execution state where evidence exists, for example:

```text
⠋ Thinking…
⠙ Exploring project…
⠹ Reading files…
⠸ Running tools…
⠼ Running tests…
⠴ Analyzing results…
⠦ Preparing answer…
```

Do not fabricate precise activity. When the runtime cannot identify the current stage, fall back to a truthful generic state such as `Working…` or `Thinking…`.

When waiting on approval, the spinner stops and the UI explicitly shows that user action is required.

## 25.4 Execution Trace model

Replace the simplistic tool-only presentation with a structured Codea-owned execution trace.

The trace must support at least these activity classes:

```text
Agent
Skill
Plugin
Tool
Subagent
Approval
Runtime/System
```

Suggested trace fields:

```text
ID
Type
Name
Status
StartedAt
FinishedAt
Duration
ParentID
Summary
Target
InputSummary
OutputSummary
ErrorSummary
Sensitivity
Truncated
Metadata
```

Do not store/render vendor DTOs directly in the TUI.

Trace lifecycle should support states equivalent to:

```text
pending
running
waiting_approval
success
failed
cancelled
```

## 25.5 Default activity rendering

Normal mode should show concise, useful execution steps:

```text
● Code Reviewer

  ⠹ Analyzing code… 5.2s

  ⎿ Agent   Code Reviewer
  ⎿ Skill   code-review
  ⎿ Plugin  codea-enterprise

  ⎿ Read    OrderService.java
     ✓ 286 lines · 0.3s

  ⎿ Grep    updateOrderStatus
     ✓ 7 references · 0.2s

  ⎿ Test    OrderServiceTest
     ✓ 18 passed · 5.1s

  ⠼ Preparing answer…
```

Failed operations:

```text
  ⎿ Test    mvn test
     ✗ 3 tests failed · 8.2s
```

Approval:

```text
⚠ Permission required

  Bash
  mvn test

  [Y] Allow once   [A] Always allow   [N] Reject
```

The UI should retain concise completed activity above the final answer rather than erasing the evidence of what ran.

## 25.6 Agent / Skill / Plugin visibility

Execution metadata should show, where real evidence exists:

```text
Active Agent
Skill loaded/used
Plugin responsible for an enterprise tool/event
Tool name
Subagent invocation
Approval request
Operation duration
Success/failure
```

Do not claim that a Skill or Plugin was used merely because it was installed or available. The trace must reflect actual execution evidence.

If the runtime/plugin protocol does not currently provide enough structured evidence for a field, extend the Codea-owned event/trace mapping rather than guessing in the renderer.

## 25.7 Reasoning presentation

Model reasoning and execution activity are separate concepts.

Reasoning continues to use runtime-provided reasoning events where available and permitted.

Default completed reasoning presentation:

```text
▸ Thinking · 5.8s
```

The user can expand/collapse supported reasoning content through the existing thinking control or its workspace equivalent.

Agent / Skill / Plugin / Tool activity is NOT hidden reasoning and remains visible in normal trace mode.

Never fabricate model chain-of-thought that the runtime did not expose.

## 25.8 View density modes

Add:

```text
/view normal
/view verbose
/view focus
```

### Normal

Default. Shows:

- Agent identity;
- Skill/Plugin activity when materially relevant;
- concise Tool name + target;
- result/failure + duration;
- approvals;
- final answer.

### Verbose

For debugging/audit. May show:

- all Normal fields;
- Subagent hierarchy;
- Tool input summaries;
- Tool output summaries;
- command/file targets;
- timing details;
- Runtime/system trace events;
- permitted reasoning content.

Raw sensitive payloads remain prohibited even in Verbose mode.

### Focus

Shows the current/last user request, a compact activity summary, and the final answer, for example:

```text
❯ 用户问题

⎿ Read 5 files · Ran 3 tools · 18 tests passed

● Final answer...
```

Focus changes presentation only; it must not discard trace data required for later expansion/audit during the active session.

## 25.9 Completion summary

After a completed task, normal mode should provide a concise footer such as:

```text
✓ Completed in 18.7s
  6 tool calls · 4 files read · 1 skill
```

Metrics must be derived from trace events rather than guessed from rendered strings.

## 25.10 DLP and trace safety

Execution visibility MUST NOT weaken existing enterprise security.

Trace input/output summaries must respect:

```text
DLP
Sensitivity classification
Secret redaction
Raw payload truncation
Maximum display sizes
Safe command rendering
```

Do not expose by default:

```text
API keys
Passwords/tokens
Sensitive headers
Full environment-variable sets
Unbounded raw Tool payloads
Sensitive RawEvent contents
```

Verbose mode is more detailed, not less secure.

## 25.11 Task 25 acceptance gate

PASS requires:

- User, Agent/Assistant, System, and Activity are visually unambiguous.
- Active Agent and selected Model are visible in the conversation context.
- Spinner animates during long-running work and stops on terminal states.
- Spinner/status text reflects actual known state or a truthful generic fallback.
- Approval state clearly replaces normal waiting state.
- Agent, Skill, Plugin, Tool, Subagent, and Approval trace events render when real evidence exists.
- Tool lifecycle is deduplicated by stable invocation identity and ends in correct terminal status.
- Durations are based on timestamps/lifecycle evidence.
- Reasoning is separate from execution trace and remains collapsible.
- `/view normal|verbose|focus` behaves as specified.
- Verbose mode cannot leak secrets or bypass DLP.
- Focus mode preserves underlying session trace state.
- Streaming performance remains bounded; high-frequency events must not trigger an uncontrolled full rerender per event/token.
- Session switching cannot leak trace/reasoning/activity from another session.

# 4. Implementation boundaries

The following are explicitly out of scope for V1.1 unless required to make the approved capabilities work:

- full parity with every OpenCode native TUI command;
- pixel-perfect Claude Code clone or use of Claude branding;
- user-personal custom-command directory;
- broad redesign of unrelated release tooling;
- replacement of the existing AgentRuntime abstraction;
- new runtime providers beyond OpenCode;
- unrelated refactors of accepted V1 functionality;
- project-level overrides of controlled enterprise commands.

# 5. Development order

Develop in this order:

```text
Task 22
  ↓
Task 23
  ↓
Task 24
  ↓
Task 25
  ↓
Task 26
```

Task 25 may consume structured execution events added by Tasks 23–24, but it must not bypass Application/Runtime boundaries to obtain them.

# 6. Engineering quality requirements

For every Task:

1. Add regression tests before/with behavior changes.
2. Prefer Codea-owned domain types at architectural boundaries.
3. Preserve Windows + offline constraints.
4. Preserve current performance strategy for buffered streaming and bounded refresh cadence.
5. Fail closed for command conflicts, unsupported runtime features, invalid custom-command metadata, and unsafe trace payloads.
6. Every user-visible machine failure that needs automation/debugging must have a stable machine classification/code where appropriate, while user-facing summaries remain readable.
7. Do not claim runtime actions, Skill use, Plugin use, or Tool outcomes without machine-verifiable evidence.
8. Do not mark a Task accepted merely because implementation exists; verification Gate + reviewer acceptance remain required.
