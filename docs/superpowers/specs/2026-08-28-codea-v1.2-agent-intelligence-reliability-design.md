# Codea V1.2 Agent Intelligence & Reliability Design

Date: 2026-08-28
Status: Approved design for implementation
Target branch: `develop`
Scope: Task 28–32
Runtime baseline: OpenCode `v1.18.11`

## 1. Goal

Codea V1.2 focuses on one outcome only: **increase the real engineering success rate of Codea Agents, especially when the company can only use medium or weak private models.**

V1.2 does not broaden Codea into a generic AI platform. It strengthens the existing General / Debug / Code Reviewer / Unit Test Generator / API Documentation workflows with deterministic local engineering capabilities that compensate for weaker reasoning, weaker context selection, and weaker self-verification.

The guiding principle is:

> 能用程序确定完成的事情，就不要再调用 Agent 判断。

The target loop becomes:

```text
User task
  ↓
Local Repo Intelligence
  ↓
Bounded task plan
  ↓
Agent executes one controlled step at a time
  ↓
Deterministic verification
  ↓
Pass ───────────────→ verified completion
  ↓ fail / missing
bounded repair loop
  ↓
checkpoint-protected continuation / restore
```

Model capability then changes how much context, autonomy, and retry budget Codea gives to the Agent; it never changes security policy.

## 2. Existing architecture remains locked

V1.2 keeps the V1.1 architecture exactly:

```text
TUI
 ↓
Application
 ↓
Codea-owned AgentRuntime Contract
 ↓
OpenCodeAdapter
 ↓
OpenCode v1.18.11
```

Rules:

1. TUI/Application MUST NOT import OpenCode vendor DTOs or vendor client types.
2. Repo Intelligence, task state, completion gates, checkpoints, and model strategy are Codea-owned capabilities.
3. OpenCode remains the first Runtime implementation, not the owner of Codea product semantics.
4. Do not add a second Runtime abstraction.
5. Existing DLP, Approval, path policy, command policy, audit, offline policy, Agent materialization, Live Trace, and session isolation remain authoritative.

## 3. Product boundaries

### 3.1 In scope

```text
Task 28 — Repo Intelligence / Code Map
Task 29 — Agent Planning & Execution State
Task 30 — Deterministic Verification Loop
Task 31 — Agent Checkpoint & Restore
Task 32 — Model Qualification & Adaptive Agent Strategy
```

### 3.2 Explicitly out of scope

V1.2 MUST NOT add:

- generic RAG platform;
- vector database;
- mandatory embedding model;
- public-cloud dependency;
- marketplace / plugin store;
- IDE extension;
- multi-agent orchestration framework;
- autonomous long-running DAG engine;
- a separate Planner LLM Agent;
- a separate Verifier LLM Agent;
- arbitrary shell execution bypassing the existing security guard;
- new external network calls for indexing, model qualification, verification, or checkpointing.

## 4. Platform and build constraints

- Go baseline remains `1.26.5`.
- OpenCode remains pinned to `v1.18.11`.
- Windows 10/11 x64 remains a first-class target.
- macOS support must not regress.
- Windows MUST NOT require WSL.
- Existing release cross-build with `CGO_ENABLED=0` must remain valid.
- No mandatory runtime compiler/toolchain may be added to the packaged target beyond existing project tooling expectations.
- Pure intranet / air-gapped operation remains supported.

### 4.1 Tree-sitter decision

Task 28 MUST NOT introduce a CGO-dependent tree-sitter Go binding in V1.2 because the current release pipeline deliberately cross-compiles Codea with `CGO_ENABLED=0`.

V1.2 Repo Intelligence therefore uses:

```text
Java/Spring deterministic extractor
+ Go standard-library AST
+ generic lexical/path fallback
+ deterministic graph ranking
```

Tree-sitter may be reconsidered only in a later version if Codea adopts an offline-shipped parser process or a verified pure-Go/WASM approach without breaking native packaging.

### 4.2 Embedding decision

Embeddings are optional future optimization, not a V1.2 dependency. The first version must prove value with local deterministic indexing and ranking. A private-model environment must not need another embedding service just to use Codea.

## 5. Task 28 — Repo Intelligence / Code Map

### 5.1 Objective

Before a coding Agent receives a task, Codea should provide a compact, task-specific representation of the repository so the model does not have to discover the project blindly through repeated tool calls.

### 5.2 Codea-owned domain

Introduce a focused package under:

```text
tui/internal/repoctx/
```

Core concepts:

```go
type SymbolKind string

type Symbol struct {
    ID        string
    Name      string
    Kind      SymbolKind
    Path      string
    StartLine int
    EndLine   int
    Package   string
}

type RelationKind string

type Relation struct {
    From       string
    To         string
    Kind       RelationKind
    Confidence float64
    Evidence   string
}

type Query struct {
    Text         string
    ChangedFiles []string
    MaxChars     int
}

type RepoMap struct {
    Summary     string
    Files       []string
    Symbols     []Symbol
    Relations   []Relation
    Unresolved  []string
    Truncated   bool
}
```

Exact implementation may split these types across focused files, but these semantics are fixed.

### 5.3 Java/Spring extraction scope

V1.2 must deterministically extract at least:

- package declaration;
- imports;
- class / interface / enum / record declarations;
- methods and constructors;
- Spring stereotypes such as `@RestController`, `@Controller`, `@Service`, `@Repository`, `@Component`;
- common mapping annotations such as `@RequestMapping`, `@GetMapping`, `@PostMapping`, `@PutMapping`, `@DeleteMapping`, `@PatchMapping`;
- constructor injection and field injection type relationships;
- exact type references;
- conservative method-call relationships when the receiver/type can be resolved.

Uncertain relationships MUST be returned as unresolved/low confidence. Class-name suffixes such as `Controller` or `Service` MUST NOT be treated as verified role evidence by themselves.

### 5.4 Go extraction scope

Use `go/parser`, `go/ast`, and standard library packages to extract:

- package;
- imports;
- functions/methods;
- types/interfaces;
- direct selector/call references where deterministically resolvable.

### 5.5 Generic fallback

For unsupported source languages, Codea still provides useful context through:

- normalized relative paths;
- file name and extension;
- exact lexical term match;
- local text search;
- Git changed-file signal.

Unsupported languages MUST degrade gracefully rather than disable the entire Repo Map.

### 5.6 Ranking

Ranking must be deterministic. Signals, in descending intent, are:

1. exact path/symbol match from user task;
2. changed-file match;
3. exact symbol/type/import reference;
4. one-hop graph neighbor;
5. lexical term match;
6. stable path/name tie-break.

No LLM call is used to rank Repo Map candidates.

### 5.7 Prompt injection

Repo Map enters the existing Codea `runtime.PromptRequest` as a synthetic Codea-owned text part before the user's real text part:

```go
runtime.TextPart{
    Text:      repoMapText,
    Synthetic: true,
    Metadata: map[string]any{
        "codea.kind": "repo-map",
    },
}
```

The original user input remains a separate non-synthetic part. This preserves Runtime abstraction and makes the context distinguishable from user instructions.

Repo Map construction must run asynchronously before the prompt is sent; Bubble Tea's Update loop must never synchronously scan a repository.

## 6. Task 29 — Agent Planning & Execution State

### 6.1 Objective

For non-trivial engineering work, the Agent must stop behaving as an unstructured chat model and execute an explicit bounded plan whose state can be observed and recovered.

### 6.2 No Planner Agent

Planning is a protocol, not a second LLM Agent. The selected working Agent creates the plan using deterministic Codea tools.

Introduce plugin tools:

```text
task_plan
task_step
task_status
```

Canonical plan shape:

```ts
interface TaskPlan {
  id: string;
  goal: string;
  steps: Array<{
    id: string;
    title: string;
    verification?: string;
    status: "pending" | "in_progress" | "completed" | "blocked";
    evidence?: string;
  }>;
}
```

Rules:

- 3–7 steps for non-trivial mutation tasks;
- at most one `in_progress` step;
- completed steps are immutable except explicit task reset/replan;
- blocked requires evidence/reason;
- plan updates are persisted atomically;
- only metadata/evidence summaries are persisted, never raw source files or secrets.

### 6.3 What requires a plan

Plan required:

- source-code modification;
- test modification;
- multi-file documentation generation tied to code changes;
- bug fix;
- refactor;
- any task that will call mutation or project-execution tools.

Plan not required:

- ordinary chat;
- read-only explanation;
- `/status`, `/sessions`, `/model`, `/doctor` and other workspace actions;
- a read-only code lookup with no mutation/execution intent.

### 6.4 Execution visibility

`task_plan` and `task_step` are normal tool telemetry and appear in existing Live Trace. Do not expose hidden model chain-of-thought.

Application maintains a compact per-turn `TaskExecutionState` derived from tool lifecycle events:

```go
type TaskExecutionState struct {
    RootTurnID        string
    PlanSeen          bool
    ActiveStep        string
    CompletedSteps    int
    MutationSeen      bool
    VerifyAttempts    int
    VerifyPassed      bool
    AutoContinuation int
}
```

This state is product truth for completion gating; it is not vendor Runtime state.

## 7. Task 30 — Deterministic Verification Loop

### 7.1 Objective

A mutating Agent task is not complete because the model says it is complete. Codea requires fresh machine verification evidence.

Hard rule:

> If a task changed project files and Codea has not observed a fresh successful verification for that task, Codea MUST NOT show the task as verified/completed.

### 7.2 Verification tool

Introduce a guarded plugin tool:

```text
verify_project
```

It reuses the existing `execCommand`, path/command policy, DLP, audit, wrapper preference, timeouts, and safe argv handling.

Initial supported verification profiles:

#### Java / Maven

```text
compile
unit tests
configured static checks when present
```

#### Java / Gradle

```text
classes / compile equivalent
tests
configured check/static tasks when present
```

#### Go

```text
go test ./...
go vet ./...
```

Unknown build systems return deterministic `NOT_CONFIGURED`; they never synthesize PASS.

Configured static checks are discovered from local project configuration. Codea must not require a new public dependency or force a public repository lookup.

### 7.3 Verification evidence

```ts
interface VerificationEvidence {
  profile: string;
  startedAt: string;
  finishedAt: string;
  stages: Array<{
    name: string;
    category: "PASS" | "FAIL" | "TIMEOUT" | "NOT_CONFIGURED" | "ERROR";
    exitCode: number | null;
    durationMs: number;
    commandSummary: string;
    outputSummary: string;
  }>;
  result: "PASS" | "FAIL" | "TIMEOUT" | "NOT_CONFIGURED" | "ERROR";
}
```

Raw secrets must not be persisted or rendered. Existing DLP remains authoritative.

### 7.4 Bounded repair loop

At Runtime step completion:

```text
no mutation
  → normal completion

mutation + verify PASS
  → verified completion

mutation + missing verification
  → synthetic continuation: run verification before claiming completion

mutation + verify FAIL
  → synthetic continuation: inspect evidence, fix, rerun verification
```

Automatic continuation is bounded to two continuations by default. After the bound is exhausted, Codea marks the task failed/unverified and stops automatically prompting the model.

The repair prompt is synthetic Codea control context, not a fake user message.

### 7.5 Completion semantics

V1.2 adds an explicit user-visible unverified outcome. `✓ Completed` is reserved for:

- read-only task with a clean terminal Runtime outcome; or
- mutating task with fresh same-task verification PASS.

A model sentence such as “fixed” or “all tests pass” cannot override the gate.

## 8. Task 31 — Agent Checkpoint & Restore

### 8.1 Objective

Before Codea lets an Agent perform risky multi-step modifications, create a recoverable local snapshot without modifying the user's project Git index, branches, or refs.

### 8.2 Shadow Git design

Use a Codea-owned shadow repository under:

```text
%CODEA_HOME%/checkpoints/<workspace-id>/git
```

with the user's project as the shadow repository's work tree. Never create Codea refs inside the project's `.git`.

Checkpoint metadata is stored next to the shadow repository:

```go
type Checkpoint struct {
    ID        string
    TaskID    string
    TurnID    string
    Commit    string
    Label     string
    CreatedAt time.Time
}
```

Workspace ID is a stable hash of normalized project root, never the raw path as a directory name.

### 8.3 Automatic checkpoints

- create baseline checkpoint immediately before a mutation-capable task starts;
- create final checkpoint after verified success;
- create a safety checkpoint immediately before restore;
- retain a bounded recent history (default 20 per workspace) and prune oldest finalized checkpoints.

### 8.4 Commands

Add controlled workspace commands through the existing registry:

```text
/checkpoint             create a manual checkpoint
/checkpoints            list checkpoints
/restore <checkpoint>   restore source state
```

Restore is blocked while an Agent response is streaming or an approval is pending.

### 8.5 Restore requirements

Restore must:

- restore tracked shadow-worktree source state exactly, including added/deleted files;
- not change project branch;
- not change project staged index;
- not create commits/refs in project `.git`;
- leave ignored build output alone;
- make a safety snapshot first;
- provide deterministic failure/recovery metadata if interrupted.

If Git is unavailable, Codea returns `CHECKPOINT_UNAVAILABLE`; it must never claim a checkpoint exists.

## 9. Task 32 — Model Qualification & Adaptive Agent Strategy

### 9.1 Objective

“Endpoint reachable” is not equivalent to “model is capable of operating Codea Agents.” Codea needs a local qualification profile and should adjust Agent strategy to the actual private model.

### 9.2 Model Capability Profile

Introduce Codea-owned profile storage keyed by `runtime.ModelRef`:

```go
type CapabilityLevel string

const (
    CapabilityUnknown CapabilityLevel = "unknown"
    CapabilityWeak    CapabilityLevel = "weak"
    CapabilityMedium  CapabilityLevel = "medium"
    CapabilityStrong  CapabilityLevel = "strong"
)

type ModelCapabilityProfile struct {
    Model            runtime.ModelRef
    ToolCalling      CapabilityLevel
    StructuredOutput CapabilityLevel
    PatchFollowing   CapabilityLevel
    Planning         CapabilityLevel
    Overall          CapabilityLevel
    QualifiedAt      time.Time
    Version          int
}
```

Profiles are local metadata under CODEA_HOME. No prompts/source contents from user projects are stored in the profile.

### 9.3 Qualification probes

Add deterministic, non-mutating probe tools:

```text
probe_tool_call
probe_structured
probe_patch
probe_plan
```

A controlled `/model-check` flow runs a fixed bounded qualification conversation with the currently selected model. Probes validate exact arguments/output contracts. They do not edit project files and do not contact public services.

Scoring rule:

```text
first-attempt contract pass → strong signal
bounded retry pass         → medium signal
bounded retry failure      → weak signal
not executed               → unknown
```

Overall level is the conservative aggregate; one strong dimension must not hide a critical weak tool-calling dimension.

### 9.4 Adaptive strategy

Unknown models default to the conservative `medium` strategy until qualified.

#### Strong

```text
Repo Map max chars: 12000
Plan: 3–7 steps
Tool strategy: normal parallelism where Runtime/Agent already permits it
Verification repair continuations: 2
Subagents: permitted when existing policy permits
```

#### Medium

```text
Repo Map max chars: 8000
Plan: 3–5 steps
Tool strategy: prefer sequential evidence → edit → verify
Verification repair continuations: 2
Subagents: avoid unless explicitly required by the selected professional Agent
```

#### Weak

```text
Repo Map max chars: 4000
Plan: exactly 3 concise steps where feasible
Tool strategy: one small mutation at a time; reread target before mutation
Verification: after each mutation group and final verification required
Verification repair continuations: 1
Subagents: disabled by strategy
Context: aggressively prefer ranked local context over broad repository dumps
```

Adaptive strategy is injected as a synthetic Codea prompt part with `codea.kind=model-strategy`.

### 9.5 Security invariant

Model capability may reduce autonomy. It MUST NEVER increase permissions, bypass approval, weaken DLP, expand path access, allow forbidden commands, or enable network access.

## 10. Cross-task integration

Final prompt construction order:

```text
1. model strategy synthetic control part
2. Repo Map synthetic context part
3. task/verification control part when applicable
4. original user text/file/symbol parts
```

The user's original content is never rewritten into the synthetic controls.

Per-task state is associated with a root task/turn ID so bounded verification continuations remain part of one engineering task rather than appearing as unrelated user turns.

## 11. Final V1.2 acceptance gates

### G1 — Architecture

- no Application/TUI import of OpenCode vendor DTOs;
- AgentRuntime remains Codea-owned;
- no second Runtime abstraction.

### G2 — Offline

- Repo indexing uses local files only;
- planning state is local;
- verification uses local project tooling/internal artifact access already allowed by policy;
- checkpoints are local;
- model qualification uses the configured private/local model only;
- zero newly required public network calls.

### G3 — Windows/native build

- `CGO_ENABLED=0` release build still passes;
- Windows x64 native tests pass;
- no WSL dependency;
- project paths with spaces work.

### G4 — Repo Intelligence

- deterministic Java/Spring and Go fixtures pass;
- exact dependency/call-chain evidence is returned where resolvable;
- ambiguity is not converted into fact;
- same input produces byte-stable Repo Map;
- budget is enforced.

### G5 — Planning

- mutation task produces bounded plan state;
- only one step can be active;
- state survives tool calls/session task continuation;
- plan telemetry appears in Live Trace without chain-of-thought leakage.

### G6 — Verification

- a mutating task without verification cannot render verified completion;
- failed verification triggers bounded repair only;
- successful fresh verification unlocks verified completion;
- retry exhaustion stops automatically;
- unknown build system is `NOT_CONFIGURED`, never PASS.

### G7 — Checkpoint

- baseline/final/safety snapshots work;
- restore reproduces source state;
- project Git branch/index/refs remain unchanged;
- Git unavailable fails visibly.

### G8 — Adaptive strategy

- model qualification is deterministic and bounded;
- profile persists by ModelRef;
- strong/medium/weak strategies change context/planning/retry behavior as specified;
- security policy is unchanged by profile.

### G9 — Existing Agent regressions

The following existing flows must remain green:

```text
/review
/test
/api-doc
/debug
normal General chat
/compact
/model
/sessions
approval flow
DLP/tool policy
Task 25 Live Trace
Task 26 native acceptance
Task 27 Windows trust/release gates
```

## 12. Implementation order

Execute in this order:

```text
Task 28 — Repo Intelligence
Task 29 — Planning & Execution State
Task 30 — Verification Loop

```

Task 32 is intentionally last because it tunes the behavior of Tasks 28–31 rather than creating a parallel capability stack.

## 13. Definition of success

V1.2 is successful when Codea can take a normal engineering request such as:

```text
“修复订单创建接口偶发重复落库的问题，并补充单测。”
```

and reliably show machine-observable behavior equivalent to:

```text
Repo Map identifies relevant Controller/Service/Repository/tests
→ Agent creates bounded plan
→ Agent modifies a small relevant surface
→ Codea records mutation
→ verify_project runs real compile/tests/checks
→ failure causes bounded evidence-driven repair
→ final PASS produces verified completion
→ checkpoints make the change safely reversible
→ weaker models automatically receive smaller context and tighter execution rules
```

That is the V1.2 product outcome. More features are not part of this release.
